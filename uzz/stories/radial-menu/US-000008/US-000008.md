## radial-menu/US-000008 — Expose Bindable Diameter and Hub Ratio for Runtime Sizing

### User Story

```
AS A developer
I WANT to bind the radial menu's overall diameter and hub proportion to other controls
SO THAT the menu stays circular, correctly sized, and layout-stable when its host layout changes
```

#### Technical Context & Constraints

* **Toolchain / Rules**: Java 25 + JavaFX + Maven; JUnit 5, AssertJ BDD assertions, and headless JavaFX tests (TestFX); AtlantaFX 2.1.0; snake_case test names
* **Phase**: N/A

#### Notes
1. Public API: `diameterProperty()`, `diameter()`, `diameter(double)`, `innerRadiusRatioProperty()`, `innerRadiusRatio()`, `innerRadiusRatio(double)`. Both properties are `DoubleProperty` and usable in bindings.
2. Defaults: `diameter = 270`; `innerRadiusRatio = 60.0 / 135.0` (approximately 0.4444).
3. Keep both existing constructors unchanged; no new required constructor parameters.
4. Derive geometry from the properties: outer radius = `diameter / 2`, inner radius = outer radius × `innerRadiusRatio`. Place the circle centre at `(diameter / 2, diameter / 2)` so local coordinates are never negative.
5. Rebuild or rescale geometry when either property changes. Preserve the selected item, its pseudo-class highlight, hover behaviour, the selection callback, and the item-to-wedge mapping across rebuilds.
6. Size the control with `setMinSize(d, d)`, `setPrefSize(d, d)`, and `setMaxSize(d, d)` so all six size constraints track the diameter.
7. Clip content to the rectangle `[0, 0, diameter, diameter]` so the outer half-stroke is clipped rather than enlarging or shifting the layout bounds.
8. Use a uniform 2 px stroke for the normal, hover, and selected segment states, defined in the component stylesheet. Keep per-state fill and border colour differences so hover and selection stay distinguishable.
9. Clamp `innerRadiusRatio` to `[0, 1)` on write so the property never reports an out-of-range value. A JavaFX binding can bypass an overridden setter, so enforce the clamp in the invalidation/change path as well and guard against re-entrant updates.
10. A non-positive diameter renders no wedges and no labels; measured width and height track `max(0, diameter)`.
11. Labels: keep `labelRadiusRatio` relative to the current radii, keep the `radial-menu-label` class, `-rm-label-fill`/`-rm-label-font-size` hooks, and mouse transparency. An explicit CSS font size is absolute; re-fit on each geometry rebuild and truncate overflowing labels with an ellipsis. The unset default remains `diameter × 0.05`.
12. Hover and selection must not change layout bounds at any diameter.
13. Demo: add a diameter slider with a live value readout, and at least one binding example sized from another control's dimension. Update `README.md` with the new API and the uniform-stroke behaviour.
14. Keep the implementation free to rebuild geometry or apply a proportional scale, provided all acceptance criteria hold.

### Acceptance Criteria

```gherkin
Scenario: Defaults preserve the current footprint
  Given a radial menu created without setting size properties
  Then diameter is 270
  And innerRadiusRatio is 60 divided by 135
  And minWidth, prefWidth, and maxWidth are 270
  And minHeight, prefHeight, and maxHeight are 270
  And layout bounds are [0, 0, 270, 270]

Scenario: Diameter can be bound
  Given a radial menu whose diameterProperty is bound to an external height of 180
  Then diameter is 180
  And the control measures 180 by 180 pixels
  And the outer radius is 90
  And the control remains circular

Scenario: Diameter changes at runtime
  Given a selected radial menu with diameter 270
  When the diameter changes to 120
  Then wedges, hub, and labels scale proportionally
  And the outer radius is 60 and the inner radius is 60 x innerRadiusRatio
  And layout bounds remain [0, 0, 120, 120]
  And the selected wedge is still highlighted

Scenario: Selection and callback survive a resize
  Given a labelled radial menu with a selection callback
  When the diameter changes and the user then clicks a different wedge
  Then the callback receives the item of the clicked wedge
  And the clicked wedge is highlighted

Scenario: Hover and selection keep the footprint
  Given a radial menu with a fixed diameter and a uniform 2 px stroke
  When a wedge is hovered and then selected
  Then layout bounds remain [0, 0, diameter, diameter]
  And the segment stroke width is 2 in normal, hover, and selected states

Scenario: Geometry is centred in its square
  Given any positive diameter
  Then the circle centre is at diameter divided by 2 on both axes
  And no wedge geometry uses negative local coordinates
  And outer stroke overflow is clipped at the square edges

Scenario: innerRadiusRatio is clamped on write
  Given innerRadiusRatio is set to -0.2
  Then innerRadiusRatio reports 0
  And given innerRadiusRatio is bound to 1.5
  Then innerRadiusRatio reports the nearest value below 1
  And the hub opening uses the clamped value

Scenario: Ratio changes reshape the hub without resizing the control
  Given a radial menu with diameter 270 and innerRadiusRatio 60 divided by 135
  When innerRadiusRatio changes to 0.25
  Then the hub opening radius is 33.75
  And layout bounds remain [0, 0, 270, 270]

Scenario: Non-positive diameter renders no wedges
  Given a radial menu with items and a diameter of 0 or less
  When the geometry is rebuilt
  Then no wedges and no labels are rendered
  And measured width and height are not negative

Scenario: Existing constructors are unchanged
  Given the two existing RadialMenu constructors
  Then code using them compiles and behaves as before
  And no new required constructor arguments exist

Scenario: Explicit label size stays fixed and truncates
  Given an author stylesheet declaring -rm-label-font-size: 18px
  And a radial menu with diameter 270
  When the diameter changes to 120
  Then label font size remains 18px
  And labels that no longer fit are truncated with an ellipsis
  And every label stays inside its wedge's usable box
  And every label keeps the radial-menu-label style class

Scenario: Default label size follows the diameter
  Given no CSS override of -rm-label-font-size
  When the diameter changes from 270 to 135
  Then the default label font size changes from 13.5 to 6.75

Scenario: Labels remain click-through after a resize
  Given a resized labelled radial menu with a selection callback
  When the user clicks any label
  Then the callback is invoked for that label's wedge
  And the wedge enters its selected state

Scenario: Demo exposes runtime resizing
  Given the demo application is running
  When the diameter slider is moved
  Then the menu diameter matches the slider value
  And the displayed diameter value matches
  And the binding example keeps the menu sized from an external control
```
